## 1. 첫 구현의 완료 범위

사용자는 AI·계정·네트워크 없이 계획을 만들고, 각자 합류 정보를 확인하고, 앱 밖에서
바뀐 상황을 반영하고, 실제 경험을 기록해 파일로 보관할 수 있다. AI는 계획 제안,
남은 일정 변경, 기록의 글 정리를 돕는 선택 경로다.

포함한다:

- 날짜 미정·한 장소·반나절·시간 미정·자정 넘김을 포함한 느슨한 계획.
- 선택한 활동과 후보, 핵심 활동과 보호할 예약의 구분.
- 공유할 합류 지점과 선택적인 개인 이동 메모. 각자 지도 앱으로 이동 확인.
- 현재 상황 반영, 다음 한 곳 교체, 남은 일정 직접 조정, AI 변경안 검토.
- 계획에 없던 실제 방문, 사진·짧은 메모, 이후 보완, AI 글 정리.
- 완전 보관용 `.datepack.json`, 선택한 기록의 텍스트 공유·복사.
- 한국어·영어, 오프라인 직접 작업, 기존 파일·기기 저장 데이터 변환.

후속 범위로 둔다: 실시간 위치 추적·교통/영업 정보 수집, 자동 경로 최적화, 두 기기
동기화·공동 편집·계정, 공개 공유 링크·이미지 카드, 자동 사진 분석, 여러 날에 걸친
여행과 서로 다른 시간대의 경로 계산. 이 기능 없이도 세 단계의 기본 흐름은 완료된다.

## 3. 데이터 계약

### 3.1 파일에 보관할 정보와 기기 정보

`DatePack`의 `manifest / plan / assets` 골격을 유지하고, `baselinePlan / experiences / revision`
을 추가한다. 기존 타입는 변환용 `Legacy*` 타입으로 분리한다. 필드 이름의 사소한 변경은
구현자가 일관되게 조정할 수 있지만 아래 정보의 의미와 저장 경계는 바꾸지 않는다.

| 데이터          | 최소 내용                                                                                        | 위치                                |
| --------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------- |
| plan            | id, title, 선택 date, 선택 가용 범위, events, candidates, places, constraints, meeting           | 보관 파일                           |
| event           | id, title, type, timing, 선택 placeId·note·assetIds, importance, protectedFields                 | 보관 파일                           |
| candidate       | id, title, 선택 장소·메모·제안자 표시                                                            | 보관 파일, 현재/다음 계산에서 제외  |

장소 레지스트리와 asset ID는 재사용한다. 경험에는 기록 당시의 장소명·지도 검색어를
함께 보관해 이후 계획의 장소 교체가 과거 기억까지 바꾸지 않게 한다. 활동이 삭제되어도
경험은 남으며 `planEventId` 연결은 선택이다. 경험은 AI 계획 patch의 수정 대상이 아니다.

기본 보관 파일은 계획·기준 계획·경험·등록된 사진 전체를 담는다. 개인 이동·현재 맥락·
진행 중인 AI 요청·undo 이력은 파일에 넣지 않는다. 개인 맥락을 포함한 기기 저장 전체
백업은 후속 범위다. 파일 내보내기에는 이 구분을 명시한다.

개인 이동은 이 기기 사용자의 정보를 기본으로 하고 상대의 출발지 등록을 요구하지
않는다. 다른 사람의 이동도 수동으로 메모할 수 있지만 본인과 상대의 위치를 자동으로
식별·동기화하지 않는다. 상대가 같은 파일을 열어도 원작성자의 개인 출발지가 따라가지 않는다.

경험의 발생 시간은 계획 날짜와 독립적으로 선택 날짜·정확/대략 시각·자유 메모를 담는다.
날짜를 바꾼 계획이나 여러 날 뒤에 남긴 메모가 실제 경험 날짜를 덮어쓰지 않는다.

### 3.2 시간의 정확한 의미

```ts
type LocalPoint = { dayOffset: 0 | 1; time: string }; // 검증된 HH:mm
type Timing =
  | { kind: 'exact'; start: LocalPoint; end?: LocalPoint }
  | { kind: 'window'; earliestStart: LocalPoint; latestStart: LocalPoint }
  | { kind: 'unscheduled'; label?: string };
```

- `window`는 활동이 그 구간에 끝난다는 뜻이 아니라 시작 가능한 범위다. UI도
  ‘14~16시 사이 시작’처럼 표시한다. 체류 예상 `estimatedDurationMinutes`는 별도 선택 정보다.
- 약속의 가용 범위는 `availableFrom / mustEndBy`다. 종료 한계를 입력했다면 계획 끝의
  제약으로 사용한다. `window`의 끝과 약속의 종료 한계를 혼동하지 않는다.
- ‘오후’, ‘전시 후’만 입력한 경우 `unscheduled.label`과 명시적 순서로 보존한다.
  다음 한 곳을 제안받는 데 정확한 시각을 요구하지 않는다.
- `dayOffset * 1440 + 분`으로 같은 약속 내 시간을 비교한다. 종료가 시작보다 작으면
  자동으로 다음 날로 고치지 않고 입력에서 다음 날을 선택하게 한다.
- 시각은 약속 지역의 벽시계 시각이다. 새 계획은 기기의 IANA 시간대를 기본 보관한다.
  날짜가 있는 오늘 판정은 그 시간대에서 한다. 서로 다른 시간대 간 이동과 DST 경계의
  실제 경과시간 계산은 지원하지 않고 시간 확인이 필요한 상태로 표시한다.
- 구파일에 시간대가 없으면 미상으로 보존하고 현재 기기 기준 표시임을 알린다.
  기기 시간대를 과거 사실로 저장하지 않는다.

### 3.3 현재·다음과 사실의 처리

1. 사용자가 알려 준 현재 맥락은 ‘마지막 확인’ 시점과 함께 표시한다. 시간이 흘렀다고
   실제 위치로 확정하지 않는다. 다른 날짜의 맥락은 현재 상태로 사용하지 않는다.
2. 맥락이 없으면 일정의 ‘예정’ 현재·다음을 표시한다. 예정과 실제를 같은 라벨로 표시하지 않는다.
3. 실제 방문/건너뜀으로 확인된 계획 항목은 남은 후보에서 제외한다. 미확인 항목은
   상태를 유지한다. 시간 미정 항목은 명시적 순서로 선택한다.
4. 새 재계획의 기본 범위는 현재 맥락/선택한 기준점 이후다. 예정 시각이 지난 미확인
   항목은 보호하되, 선택해서 다시 포함할 수 있다. 모든 지난 항목을 먼저 묻지 않는다.
5. ‘지금 여기’ 저장은 현재 맥락을 바꾼다. 사용자가 현재 방문으로 명시한 경우에만
   최소 방문 기록을 함께 생성한다. ‘여기로 가는 중’은 방문 기록을 만들지 않는다.
6. 다음 목적지를 직접 알려 준 경우 기존 후보 선택 또는 새 활동 추가로 반영한다.
   시간은 미정이어도 된다. 과거 활동의 완료/건너뜀을 유추하지 않는다.

## 4. 변경·검증·AI 계약

### 4.1 같은 변경안을 미리 보고 적용한다

코어에 다음 책임을 분리한다. 구체적인 함수명보다 실행 순서와 보장 사항이 기준이다.

1. `parseProposal`: 형식과 값의 구조를 읽는다.
2. `prepareProposal`: 현재 pack과 context, 변경 범위를 받아 복제본에 모든 작업을 적용한다.
   새 ID는 이 단계에서 한 번 생성하며 변경 요약·완성된 결과·검증 이슈·기준 revision을 반환한다.
3. `validatePrepared`: 참조 무결성, 시간, 보호, 범위, 과거 사실, 이동·종료 제약을 검사한다.
4. 앱의 `commitPrepared`: 기준 revision/context와 저장소의 현재 상태를 다시 대조하고,
   미리 본 복제본을 원자적으로 저장한다. 적용할 때 patch를 다른 상태에 재해석하지 않는다.

보호 위반은 변경 전 데이터로 판정한다. AI가 같은 답안에서 보호를 해제하거나
고정 항목을 삭제·재생성하는 우회를 허용하지 않는다. 직접 해제는 별도 명시적 편집이다.

결과는 `error / conflict / uncertain`으로 구분한다. `error`는 적용 불가다. 나머지는
문제가 있는 항목만 확인하고 적용할 수 있다. 아무 이슈가 없다는 것은 제공된 정보 안에서
충돌을 못 찾았다는 의미이며 영업·실시간 교통 검증 완료를 뜻하지 않는다.

이동 분을 모르면 0으로 간주하지 않는다. 비교에 필요한 이동/체류 정보가 없으면
관련 구간을 `uncertain`으로 표시한다. 활동 시각이 모두 미정이라면 거짓 출발 권장을
만들지 않는다. 정확한 출발 권장은 해당 개인/공동 구간의 목적지·시각·이동 예상이
모두 있고 출발 맥락이 맞을 때만 예상치로 표시한다.

### 4.2 AI v2 요청과 결과

- 모든 요청에 `requestId / packId / baseRevision / contextRevision / generatedAt / kind`
  를 넣는다. 반환되는 결과에도 식별값을 요구한다. 누락되거나 다르면 자동 보완하지 않고
  기존 계획을 유지한 채 다시 요청할 문구를 제공한다.
- `kind`는 새 계획 / 다음 한 곳 변경 / 남은 일정 변경 / 기록 글 정리로 나눈다.
  새 계획은 앱이 빈 초안과 pack ID를 먼저 만들어 요청하고, 결과는 그 초안을 채운다.
  이미 사용 중인 다른 pack을 덮어쓰지 않는다. 제목 미입력 시 ‘새 데이트’를 기본값으로 쓴다.
- 새 계획 초안에는 사람이 읽을 활동·장소와 임시 참조만 허용하고 앱이 영속 ID를 배정한다.
  변경안은 기존 ID와 새 항목의 임시 참조를 함께 지원한다. 장소 생성과 빈 계획 삽입을 지원한다.
- 첫 변경안은 선택한 범위의 **교체 결과**를 반환하게 한다. 범위 안의 기존 활동은 ID로
  유지·수정·제외를 식별하고 새 활동은 임시 참조를 쓴다. 범위 밖 ID를 수정하거나 과거
  기록을 반환하면 거부한다. 제외된 기존 활동은 변경 요약에 명시한다.
- `scope`는 진입 행동으로 정하고 허용 대상 ID를 요청에 고정한다. 시간 미정인 범위도
  순서와 사용자 선택으로 정한다. 보호된 활동은 요청 범위 안에서도 변경 불가다.
- 계획이나 실제 기록이 수정되어 `baseRevision`이 달라지면 답안을 그대로 적용하지 않는다.
  입력을 보존한 채 새 요청을 만들 수 있게 한다. 자동 병합·자동 재기준화는 첫 범위에서 제외한다.
- 시간만 흘렀으면 최신 시각으로 영향 검사를 다시 하고 새 검토 결과를 보여준다. 사용자가
  현재 맥락을 바꾸었다면 `contextRevision` 불일치로 새 요청이 필요하다.
- 적용 완료 request ID를 기기에 보관한다. 다시 붙여넣으면 이미 적용된 요청임을 알린다.
  계획 undo도 revision을 새로 만들기 때문에 과거 답안이 다시 유효해지지 않는다.
- 기록 글 정리는 선택한 경험 ID와 원문만 보낸다. 결과는 별도 글 초안이며 활동·방문 사실을
  변경하는 연산을 허용하지 않는다. 사실 보존을 기술적으로 보증한다고 표현하지 않고,
  원문과 결과를 사용자가 확인한 뒤 저장한다.

AI 대화 과정의 자유로운 질문·논의와 최종 기계 판독 결과를 구분한다. 요청문은 최종
선택 후에만 구조화한 결과를 내도록 안내한다. 복사·공유 전에 전달할 맥락을 보여준다.

### 4.3 중단·복귀·저장 실패

요청의 단계는 `작성 → 전달 준비 → 답안 대기 → 검토 → 적용 완료`다. 단계와 입력은
기기에 자동 저장한다. 공유 취소는 전송 완료로 표시하지 않고 복사 대안이 남는다.
앱 재시작 후 진행 중 요청은 원래 pack에만 연결해 재개한다.

pack·경험·undo·요청 완료 표시는 한 IndexedDB 트랜잭션으로 저장한다. 저장 실패 시
적용 완료 UI로 넘어가지 않고 입력/검토를 보존한다. 탭마다 기대 revision을 대조해
동시 수정은 덮어쓰지 않고 최신 상태 재불러오기로 처리한다. 다중 사용자 동기화는 아니다.

## 5. 기존 데이터 변환과 내보내기

- 파일 format 3.0을 새 표준으로 쓴다. npm 버전과 파일 버전은 별개다. 배포를 만들 때
  core 0.3.0 및 앱 릴리스 노트를 갱신하되 게시·배포는 구현 작업에 포함하지 않는다.
- v1 ZIP·v2 JSON의 ID, 제목, 메모, 사진, 장소, 제약, Plan B는 보존한다. 시간은 exact로
  옮기고 기존 정렬 결과를 명시적 순서로 초기화한다. `fixed: true`는 전체 보호로 옮긴다.
- 기존 `travelMinutes`는 바로 앞 활동에서의 공동 이동 추정으로 옮기되 출처를 legacy로
  표시한다. 첫 활동의 값은 출발지가 불명인 추정으로 보존하고 개인 출발 안내에 쓰지 않는다.
- Plan B의 텍스트·대상 ID는 그대로 보존한다. 첫 구현은 텍스트 표시와 명시적 전환을 유지하고,
  일정 실제 교체가 필요한 경우 일반 변경 검증을 통과시킨다. 자동 추천이나 자동 전환은 없다.
- 기기 DB는 v3로 올려 새 저장 구조·요청·undo·원본 백업 영역을 추가한다. 기존 저장소를
  삭제하지 않고, 읽기 시 순수 변환→검증→새 형식 저장을 수행한다. 실패하면 원본을 보존한다.
- 구파일만 가져오면 방문 이력은 알 수 없다. 같은 기기에 runtime이 있으면 명시적
  completed/skipped만 경험으로 옮긴다. 실제 시각은 미상, migration 출처를 남긴다.
  pending/current는 방문 사실로 변환하지 않는다. 지연·Plan B 선택은 별도 legacy 맥락으로 보존한다.
- 변환 ID를 원래 plan/event ID에서 결정해 재실행해도 같은 경험이 중복 생성되지 않게 한다.
  진행 중 요청과 undo는 구파일에 없으므로 새로 추정하지 않는다.
- 지원하는 각 major의 알려진 minor는 1.0·2.0·3.0이다. 같은 major의 미래 minor는
  원본을 유지한 읽기 전용으로 연다. 알려진 구조로 읽을 수 없는 경우에는 내용을 억지로
  복원하지 않고 지원 범위와 원본 보관을 안내한다. 편집·재저장으로 모르는
  필드를 잃게 하지 않는다. 다른 미래 major는 명확히 거부한다. 해당 버전 지원은 이후 업데이트다.
- 기본 내보내기는 3.0 보관본이다. 새 의미를 잃는 v2 다운그레이드는 제공하지 않는다.
  구앱이 열 수 없다는 점은 내보내기 설명에 명시한다. 원본 다운로드는 별도 가능하다.
- 공유 텍스트는 선택한 경험과 선택한 메모만 담는다. 앱이 없어도 읽을 수 있으며 개인
  이동·진행 중 요청·기준 계획은 자동으로 포함하지 않는다. 원본 보관본은 변경하지 않는다.

- P4 이후 진행. 특정 AI 서비스가 공유 목록에 없는 상황은 복사 경로로 완료 가능해야 한다.

### P6. 통합 검증·문서·릴리스 준비

- 기존 테스트를 새 계약에 맞게 갱신하고 `pnpm verify`, `pnpm build`를 통과시킨다.
  아래 인수 경로와 조사 문서의 C01~C40을 완료/후속/명시적 제한으로 추적한다.
- 브라우저와 설치 PWA의 복귀·오프라인·저장·내보내기를 확인한다. 실제 iOS/Android 기기를
  사용할 수 없는 환경에서는 검사 불가로 남기고 실기기 검증 완료라고 쓰지 않는다.
- README, core README, CHANGELOG, 예제 파일, 파일 버전·AI 형식 설명을 갱신한다.
- 구현 완료와 출시 준비를 구분한다. 자동 검사·브라우저 인수 통과는 구현 완료 기준이고,
  플랫폼별 실기기 확인은 모바일 지원을 검증했다고 주장하기 위한 출시 확인 항목이다.

## 7. 필수 인수 경로

1. **각자 합류·반나절:** A와 B가 다른 곳에서 출발해 14~17시에 만난다. 한 활동과
   후보만 저장해도 된다. 각자 이동 확인은 다르고 오전·저녁 일정은 생성되지 않는다.
2. **앱 밖의 결정:** 식당·전시 계획을 만든 뒤 앱을 닫았다가 다른 카페에서 연다.
   현재 카페와 이미 정한 서점만 입력한다. 전시 방문 여부는 미확인으로 남고, AI 없이 이어진다.
3. **보호·오래된 답안:** 예약을 보호한 채 남은 계획을 AI에 요청한다. 그 사이 직접
   변경하면 과거 답안은 적용되지 않는다. 새 요청의 유효 결과는 미리 본 내용 그대로 적용된다.
4. **나중에 기록:** 당일 앱을 한 번도 쓰지 않고 며칠 뒤 사진·한 줄 메모를 남긴다.
   실제 시각 없이 저장하고 선택한 문구만 공유한다. 보관 파일을 새로 열어도 경험이 남는다.
5. **중단·오프라인:** 요청문 작성/답안 검토 중 앱을 닫았다가 복귀하고, 네트워크가 없어도
   직접 계획 변경·기록을 저장한다. 저장 실패는 성공으로 표시되지 않는다.
6. **호환성:** 기존 파일과 기기 runtime을 변환해 명시적 완료 기록만 복원한다.
   미래 minor 파일은 읽기 전용이며 원본을 그대로 받을 수 있다.

출시의 기능 기준은 사용자가 체크리스트를 많이 채우는 것이 아니라, 위 경로를 불필요한
시간 입력·과거 복원·AI 호출 없이 완료할 수 있는가다. 행동 효과의 수치 목표는 현장
측정 뒤 정하며 지금 임의의 성공률·소요시간으로 가정하지 않는다.

## 8. 추가 사용자 결정이 필요한 경우

현 범위에서는 추가 제품 결정을 요청하지 않고 P0부터 순서대로 구현할 수 있다.
새 계정/외부 유료 서비스가 필요해지거나, 원본을 보존하지 못하는 변환이 필요하거나,
공동 편집·공개 링크 같은 후속 범위를 당겨야 할 때만 범위 변경을 논의한다.
자료형 이름, 모듈 분리, 테스트 도구, 작은 UX 문구는 구현 과정에서 처리한다.
